- Active chat, inline specialists and text summaries use the shared Cerebras Chat Completions adapter and active provider-key pool. Do not route text generation through Lovable AI Gateway.
- Speech-to-text and other audio/media operations remain on their dedicated provider integrations unless Cerebras explicitly supports the required audio API; do not confuse an audio gateway or Git connector with text-model inference.
- Shared usage availability checks use the caller's owner-scoped client before provider-token access; costly discrete audio/vision operations also debit atomically. Why: exhausted accounts must not bypass chat limits through media endpoints; token gating is not continuous-session metering.
- Recompute replyLanguageInstruction from the latest user message at each agent-loop step, after persona and saved context; people-bot uses the invoking member's message. Why: language switches, tool outputs and other participants must not override the current user's language or dialect.
- Cerebras tool calls use the existing OpenAI-compatible SSE parser with `reasoning_effort: "medium"` for agent turns (low gave shallow, manual-instruction answers); one-shot replies such as hosted Telegram bots stay "low".
- The agent loop holds each step's text until the step ends, nudges a first-answer refusal once, a technical ask (IDs/code/API steps) once and printed tool calls at most twice, and cooling Cerebras keys are reused only when no ready key exists. Why: act-first behavior without unbounded usage or false "not configured" failures.
- Agent-published web pages are agent_documents rows served by /api/public/site/$siteId with a CSP sandbox header. Why: user-generated HTML gets a live link without reading the app's session or storage.
- Hosted Telegram bots save every received update to the owner-only telegram_inbox (30-day retention); personal Telegram Business chats are answered only when business_reply is on. Why: the agent reads the user's messages without storing the bot token or replying on their behalf uninvited.
- Agent turns end with a tool-free final step and a wrap-up note near the step budget; blocked-site reads get a switch-source note. Why: big tasks must deliver a result instead of failing at the limit or trusting anti-bot pages.
- Text and agent turns go through cerebrasRequest/getCerebrasKeys: provider_api_keys rows with provider "coarena" are tried first (CoArena OpenAI-compatible endpoint; agent steps pass a per-role model chain from src/lib/models/modelRouter.ts, other callers COARENA_MODEL), then Cerebras keys with CEREBRAS_MODELS.text; any CoArena failure falls through to Cerebras without waiting. Tool names sent to the model must be unique. Never hardcode model ids in the loop or bot defaults, and trim whitespace-only step text. Why: one switch per provider, strongest model first with a free fallback, and CoArena rejects duplicate tool names.
- The newest user message's photos go to the model as image_url parts (older ones as a text note). Why: the main model sees images without bloating history.
- "Always allow" per app is stored in server-written auth app_metadata.auto_approve_apps; request_integration_action executes directly for those apps and the loop continues (only approval cards end the turn). Why: users stop re-approving trusted apps, the browser cannot grant itself approvals, and multi-step tasks are not cut off.
- Agent steps pick a CoArena model by role (big-task planning/final answer, fast chat, web, coding, vision) via modelRouter; a failing model tries the next in its chain, then Cerebras. Why: strongest model only where it matters, cheaper fast models elsewhere, no failed replies.
- Chat adapters must forward the selected per-step CoArena chain; Apify uses live discovery and signed owner-bound run documents, and validated social payloads render as chat cards. Why: routing must apply to real chat without catalogue bloat or cross-account run access.
- Runtime credentials read service-only external Supabase Vault; callbacks use an independent HTTPS app origin and the migrated original scheduler value. Why: account deletion must not orphan scheduled tasks or invalidate existing signatures.
- Read-only lookups requested together in one model step run concurrently, and discovery calls are cached per task. Why: fewer wasted steps.
- Routine completion uses the existing service-only finish_routine_run transaction and preserves manual pauses; operator setup allows only an explicit exact test-host exception. Why: partial message/schedule writes and stale destinations must not masquerade as successful recurring work.
